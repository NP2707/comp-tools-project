Several directions can give a more useful account of purpose than one hard cluster per skill. The weighted LSA/K-means baseline and a [static template audit](../results/template-audit/FINDINGS.md) have been implemented; the other experiments below remain proposals.

1. **Separate action, object, domain and output.** Label a skill as, for example, `generate / tests / React / test files`, or `review / code changes / Python / prioritized findings`. Add a mechanism facet such as MCP or CLI rather than mixing mechanism with purpose. Annotate a modest stratified sample, allow multiple labels, and use it to evaluate extraction or classification. This is the strongest route to an interpretable taxonomy.

2. **Compare multilingual semantic embeddings.** Embed names/descriptions, then cluster with HDBSCAN or K-means and label groups from representative descriptions and enriched terms. [Sentence-BERT](https://arxiv.org/abs/1908.10084) establishes sentence embeddings for cosine similarity; a multilingual model would need a separate model choice and evaluation on this corpus. [BERTopic](https://arxiv.org/abs/2203.05794) combines document embeddings, clustering and topic representation. Compare against our baseline on reviewer-labeled pairs and cross-language paraphrases, not just silhouette. This specifically targets the language-driven and unresolved groups.

3. **Allow overlapping purposes.** [NMF topic models](https://scikit-learn.org/stable/modules/decomposition.html#nmf) can represent a document as a nonnegative mixture of components. A skill may combine testing, security and deployment. Inspect component words and evaluate multi-label assignments; topic weights are not automatically calibrated confidence. This avoids forcing every multifunction skill into one bucket.

4. **Measure declared purpose versus procedural evidence.** Extract the claimed action/output from metadata, then look for supporting steps, file types, commands, API names and bundled-script imports. Review disagreement candidates for vague descriptions, generic templates, stale documentation or multiple functions. Our body/metadata partition disagreement identifies representation sensitivity; it does not itself establish inconsistent behavior. Static analysis can provide evidence without executing untrusted skill scripts.

5. **Study whether templates hide purpose diversity.** Within exact- and near-duplicate families, measure how much descriptions, domains and expected outputs vary while procedure text stays constant. The initial static audit confirms a 25-member generic template across different declared domains, but this family alone supplies 92.7% of cross-cluster pairs. Several other crossing pairs describe the same core task. Distinguish substantive instructions, generic scaffolds and delegating wrappers using independent annotations; report family-level results and include within-cluster controls. This direction ties purpose discovery directly to the project's existing MinHash/LSH work.

6. **Evaluate purpose through task-to-skill retrieval.** Write realistic task requests, have reviewers judge applicable skills, and compare retrieval by name, TF-IDF, LSA and sentence embeddings. Report recall@k, ranking quality and coverage across domains. Keep near-duplicate families in the same evaluation partition to reduce leakage. Success on held-out tasks is stronger evidence of a useful purpose taxonomy than visually attractive clusters.

A practical next sequence is to annotate 100–200 skills or pairs, compare a multilingual representation, and then pursue template-versus-purpose diversity as the main research question. Annotation size and strata should be adjusted after checking category coverage. These experiments can establish whether the observed groups describe real functionality rather than vocabulary, language or boilerplate.
